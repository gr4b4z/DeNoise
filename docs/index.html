Alert hub · .NET 10 · React 19 · PostgreSQL only

Fewer alerts. Every one of them owned, verified and explained.

DeNoise ingests alerts from Azure Monitor, MongoDB Atlas and generic webhooks, deduplicates them into episodes, assigns an owning team, auto-resolves on policies you control — with recorded evidence — verifies that monitoring is actually still watching, and delivers signed, templated notifications to any webhook receiver or mailbox.

How it works

From raw webhook to owned episode to verified closure

Every step commits to PostgreSQL before anything is acknowledged. Processing is a durable, retryable pipeline with idempotent internal effects; the guarantee is at-least-once processing, exactly-once state, not exactly-once delivery.

1 · IngestPOST /ingest/{keyId} stores the raw payload and a normalise job in one transaction, then returns 202.
2 · NormaliseThe integration's active mapping (JSONPath DSL) produces a canonical event; failures are quarantined, never dropped.
3 · IdentifyOrdered identity components form a fingerprint; delivery key deduplicates repeats; ordering rules reject stale recoveries.
4 · EpisodeOpen, update or resolve the episode under a row lock; timeline and audit written in the same transaction.
5 · RouteRouting predicates pick the owning team and destinations, with an explanation and a mandatory triage fallback.
6 · DeliverOutbox rows are dispatched as templated, HMAC-signed webhooks or email; permanent failures fall back and raise an alert.
7 · WatchLifecycle timers, coverage checks and heartbeats keep closing and re-opening honest.
Features

What is actually in the box

Deduplication into episodes

One episode per firing condition, not per webhook. Identity is an ordered list of components you define per mapping (scope, environment, resource, rule, dimensions); repeats bump count and last_seen, severity is max-of-policy.

  • Delivery-key idempotency for duplicate webhooks
  • Ordering by occurred_at with clock-skew allowance
  • Recovery-before-open and old-recovery handled explicitly

Auto-resolve with evidence

Closure is a fact with a reason and evidence, not a timeout. Sources with explicit recovery close on source; quiet sources close on inactivity only when coverage proves they are still reporting.

  • Reasons: source_resolved, verified_resolved, inactivity_timeout, expired_unverified, manual_close, source_cancelled
  • Eight guards before an inactivity close (stale timer, backlog, mapping failures, coverage, policy re-check, state verification…)
  • Impact preview before activating a policy version; rollback

Ownership and routing

Predicate-based routing rules assign a team and destinations; nothing is ever unowned — unmatched episodes go to the triage team with the reason visible on the episode.

  • Per-episode routing explanation
  • Escalation policies: ack_deadline, escalation steps
  • Team overview: unassigned, overdue, ageing, stale

Coverage and heartbeats

Silence is a signal. Each integration has a coverage state (healthy → delayed → degraded → unavailable) fed by canaries or API probes; when a source goes quiet, auto-resolve is suspended and a coverage episode opens.

  • Registered heartbeats (dead man's switch) with interval or cron schedules, IANA zones, DST-safe
  • Ping URL with /start, /fail, /exit/{code}
  • Pause, resume, token rotation, YAML export/import

Notifications you can trust

Two channels only — outbound webhook and SMTP — and everything else is a template. Built-ins: generic-json, teams-adaptive-card (Workflows), slack-blocks, plain-text.

  • Liquid templates in a sandboxed engine (200 ms, 256 KiB, no scripting)
  • HMAC-SHA256 signature, stable delivery id across retries
  • Mandatory fallback destination; event-type subscriptions

Suppression and grouping

Silences and maintenance windows have a predicate scope, a mandatory reason and wall-clock bounds in an IANA zone. When a window ends with the condition still active, one summary per team destination is sent.

  • Grouping rules: match, key, window, first_only | first_and_new_critical
  • Heartbeats auto-pause inside covering maintenance windows

Config as code and audit

Export every active policy of every kind as one YAML bundle (denoise_config: 1); import with a dry-run diff (unchanged / new_version / create) before applying.

  • Every mutation audited with before/after; keyset-paged audit API
  • Mapping, template, heartbeat and policy versions are immutable

Shadow mode and divergence

Run an integration in shadow: full processing, zero notifications. Compare hub state with the source's own state API for every open episode and get an agree / diverged / unknown report before you cut over.

Operator UI

Virtualised work queue with URL-addressable filters and saved views, keyboard triage, episode detail with identity, lifecycle, routing explanation and timeline, live updates over SSE with explicit stale/disconnected states, light/dark, axe-tested.

Concepts

The model, in five definitions

Episode

The unit of work. One episode represents one firing condition identified by its fingerprint. It has two independent state dimensions:

DimensionStatesChanged by
Conditionfiring · unknown · resolved · not_applicablethe source, verification, timers, coverage
Handlingnew · acknowledged · closed (+ suppressed rows)people: ack, assign, take over, close, restore

A recovery closes the condition; a human closes the handling. A resolved episode that fires again after closed_at opens a new episode linked to the previous one — recurrence is counted, history is never rewritten.

Fingerprint and delivery key

Two different mechanisms. The delivery key (source event id, or a body hash with volatile paths excluded) drops duplicate webhook deliveries. The fingerprint — canonicalised identity components from the mapping — decides which episode an event belongs to. Change identity, bump identity_version.

Integration and mapping

An integration is an authenticated source with an ingest key, a type (azure_monitor, atlas, generic), a coverage method, lifecycle defaults, an access scope and an ordered list of versioned mappings. A mapping is a declarative YAML document (07 DSL): fields, required, identity, enrich, applies_when. Activation is refused if any stored sample fails.

Policy

Versioned, one active version per id, four kinds: routing, escalation, lifecycle, grouping. Lifecycle policies carry the profile (explicit_recovery, repeating/inactivity, informational) and the inactivity formula. Every activation can be previewed for impact and rolled back.

Destination and template

A destination is a webhook URL (or mailbox) with encrypted secrets, headers, a signing secret, a subset of event types, a template and a mandatory fallback. Templates are Liquid, versioned, validated against a sample before activation.

Coverage

Per-integration proof that the source is still able to report: canary rule, API probe or registered heartbeat. Coverage loss opens its own episode and suspends inactivity-based closes for that integration until recovery_successes_required consecutive successes.

Environments

Every environment a team is accountable for is ingested — production, staging, development — but separated by policy, not refused at the door: one integration per environment (own token, rate limit, scope, shadow flag), production gets the full routing and escalation path, staging notifies without escalating, development runs in shadow mode, and ephemeral preview stacks are not ingested at all. The queue opens on environment ∈ {production, unknown} so unclassified alerts are never hidden; other environments are one click away.

For integrators · inbound

Ingestion contract

The ingest host is public and minimal: /ingest/*, /hb/*, /healthz/*. It never returns 200 before the raw event is committed and never echoes the input.

Send an alert

POST /ingest/{integrationKeyId}
Authorization: Bearer <integration token>
Content-Type: application/json          # any type; stored as-is
X-DeNoise-Source-Time: 2026-09-13T10:15:00Z  # optional: occurred_at when the body has none
X-MMS-Signature: <hmac>               # Atlas only; algorithm per integration config

# body ≤ 256 KiB (limits.payloadBytes)
StatusMeaning
202{ "eventId": "…", "receivedAt": "…" } — durably accepted; processing is asynchronous
401unknown key id or invalid token (constant-time compare, no distinction leaked)
413payload over the limit
429per-integration rate limit (initial 600/min) — honour Retry-After
503durable acceptance failed, nothing committed — retry

No other status codes exist. Tokens are shown once at integration creation or rotation (POST /api/v1/integrations/{id}/rotate-ingest-token) and stored as Argon2id hashes.

Azure Monitor and MongoDB Atlas

Reference mappings are seeded active when you create an integration of that type: Azure Common Alert Schema (metric, log, activity, Resource Health, Service Health; canary rules become heartbeats), Atlas webhook with X-MMS-Event fallback and HMAC verification (sha1/sha256, base64/hex, required or verify-only). Point the action group / Atlas alert at the ingest URL with the bearer token and you are done.

Heartbeat ping (dead man's switch)

Register a heartbeat in the UI or via POST /api/v1/heartbeats; the response contains the ping URL exactly once. Have the job call it on schedule — silence past the grace period opens an episode owned by the declared team.

GET|POST /hb/{keyId}.{token}              # success
POST     /hb/{keyId}.{token}/start        # run started
POST     /hb/{keyId}.{token}/fail         # explicit failure
POST     /hb/{keyId}.{token}/exit/{code}  # exit code; non-zero = failure
# optional text body ≤ 16 KiB stored as the run's output tail
# 200 { "ok": true } · 404 unknown or rotated · 429 per-key limit (60/min)

# cron example
0 2 * * *  /usr/local/bin/backup.sh && curl -fsS -X POST https://ingest.example/hb/k7q2m9x1p4r8.$TOKEN \
           || curl -fsS -X POST https://ingest.example/hb/k7q2m9x1p4r8.$TOKEN/fail
For integrators · outbound

Receiving notifications

Every notification is an HTTP request to your destination URL with a body rendered from the destination's template. You choose the event types you want (episode.opened, episode.acknowledged, episode.escalated, episode.resolved, episode.closed, episode.summary_after_suppression, coverage.lost/restored, heartbeat.missed/recovered, hub.delivery_failure, …).

Headers on every request

X-DeNoise-Delivery-IdUUID, stable across retries — deduplicate on it
X-DeNoise-Eventevent type, e.g. episode.opened
X-DeNoise-TimestampUnix timestamp used in the signature
X-DeNoise-Signaturev1=<hex> when the destination has a signing secret
User-Agentconfigurable; plus any static headers you set on the destination

Retry and fallback semantics

  • Retried: 5xx, 408, 425, 429 (honours Retry-After), timeouts.
  • Permanent: any other 4xx and template render failures → delivered to the fallback destination once and hub.delivery_failure raised.
  • Before sending, the dispatcher re-checks relevance (episode state, suppression) and coalesces superseded updates.
  • Duplicate external delivery is possible when your endpoint accepts but the response is lost — hence the delivery id.

Verify the signature

Receiver recipe: hex(hmac_sha256(secret, timestamp + "." + rawBody)). Compare constant-time; reject stale timestamps according to your own tolerance.

# Node.js
import { createHmac, timingSafeEqual } from "node:crypto";

export function verify(req, rawBody, secret) {
  const ts  = req.headers["x-denoise-timestamp"];
  const sig = req.headers["x-denoise-signature"] ?? "";
  const expected = "v1=" + createHmac("sha256", secret)
        .update(ts + "." + rawBody).digest("hex");
  return sig.length === expected.length
      && timingSafeEqual(Buffer.from(sig), Buffer.from(expected));
}
# Python
import hmac, hashlib

def verify(headers, raw_body: bytes, secret: str) -> bool:
    ts  = headers["X-DeNoise-Timestamp"]
    sig = headers.get("X-DeNoise-Signature", "")
    mac = hmac.new(secret.encode(), (ts + ".").encode() + raw_body, hashlib.sha256)
    return hmac.compare_digest(sig, "v1=" + mac.hexdigest())

Built-in templates

generic-json (full episode model), teams-adaptive-card (Power Automate Workflows HTTP trigger), slack-blocks (Block Kit), plain-text. Clone and edit in the UI with live preview against a sample or a real episode; POST /api/v1/webhook-templates/render previews a draft.

Application API /api/v1

The OpenAPI document generated from DeNoise.Api is the executable contract and is checked for drift in CI. Full document: openapi/v1.json · human-readable contract: 06-api-contract.md.

Conventions

ErrorsRFC 9457 application/problem+json; type is urn:denoise:error:*, plus traceId and errors[] for validation

Deploy

Run it

Four backend images from one Dockerfile (--build-arg HOST=Api|Ingest|Workers|Migrator), each listening on :8080 as a non-root user. The React SPA in web/ builds to static files. PostgreSQL 16 is the only required service; SMTP and an OTLP collector are optional.

The app profile builds and runs the full hub; the migrator runs first and the hosts wait for it.

git clone https://github.com/gr4b4z/DeNoise.git && cd DeNoise
docker compose --profile app up --build -d

# api      http://localhost:8080   (/api/v1, /auth, SSE, /healthz/ready)
# ingest   http://localhost:8081   (/ingest, /hb)
# workers  http://localhost:8082   (/healthz only; roles processing,scheduler,dispatcher)
# mailpit  http://localhost:8025   (catches SMTP on :1025)
# postgres localhost:5432          (denoise / denoise / denoise)

# web UI (dev server proxies /api and /auth to :8080)
cd web && pnpm install && pnpm dev        # http://localhost:5173

Sign in with the bootstrap admin account (password from DeNoise:Auth:Local:BootstrapPassword / the Helm secret; must_change_password is forced on first login). dotnet run --project src/DeNoise.Migrator -- seed-dev additionally creates a triage team and a generic-webhook integration and prints its ingest token.

Prerequisites: .NET 10 SDK, Node.js 22 + pnpm, Docker (for PostgreSQL and Testcontainers).

docker compose up -d postgres mailpit

dotnet run --project src/DeNoise.Migrator -- seed-dev      # migrate + dev integration

Operate

Health, metrics, retention

Health endpoints

On every host: /healthz/live, /healthz/ready, /healthz/startup. Readiness includes the database. The /hub screen and GET /api/v1/hub/health show component heartbeats, per-kind queue depth, outbox lag, failed jobs and the external dead-man status.

OpenTelemetry

Traces and metrics via OTLP when OTEL_EXPORTER_OTLP_ENDPOINT (or Otel:Endpoint) is set; Serilog JSON to stdout. Metric names:

  • denoise_ingest_accepted_total · denoise_ingest_rejected_total
  • denoise_episode_transitions_total · denoise_closure_total · denoise_episode_open · denoise_unassigned_open
  • denoise_delivery_attempts_total · denoise_notification_latency_seconds
  • denoise_mapping_failures_total · denoise_job_queue_depth · denoise_job_oldest_age_seconds · denoise_scheduler_lag_seconds
  • denoise_coverage_state · denoise_heartbeat_state

Retention

alert.raw_event is partitioned daily; partitions older than 30 days are dropped (never today−1 or newer). Row rules delete normalised events of closed episodes > 90 d, closed episodes > 12 months, delivery attempts / terminal outbox / done jobs > 30 d, audit > 12 months. Open episodes are never touched. Daily 02:00 UTC; POST /api/v1/hub/retention/run on demand.

Self-monitoring rule

The hub must never be the only monitor of itself. Set externalDeadmanUrl so the scheduler pings an independent dead-man service every minute, and have an external system check /healthz/ready, queue lag and dispatcher progress. Runbook: hub-failure.md.

Security

  • Ingest tokens and PATs hashed with Argon2id; destination URLs, headers and secrets encrypted at rest, masked in the UI, never logged
  • Access scope derives from the authenticated integration, never from payload labels
  • Login lockout per user and per IP, breached-password list, forced password change, server-side sessions, CSRF for cookie sessions
  • Non-root containers; no scripting anywhere (mapping DSL and Liquid templates are logic-limited)

Load and recovery drills

k6 ingest load test: k6 run -e INGEST_URL=… -e TOKEN=… build/loadtest/ingest-k6.js. Quarterly backup/restore drill: build/backup-restore-drill.sh <database>. Pilot runbook, usability script and per-route decommission checklist under docs/pilot/.
